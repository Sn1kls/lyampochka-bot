# SPEC: Telegram-бот графіків відключень світла (Тернопільобленерго)

Документ для Claude Code. Мета: реалізувати бота за цим ТЗ, працюючи фазами (розділ 12) і комітячи після кожної.
Мова бота й повідомлень: українська. Мова коду, коментарів і назв: англійська.

---

## 1. Мета і межі

**Назва продукту:** «Лямпочка». Telegram: `@lyampochka_bot`. Назва живе лише в текстах (`adapters/telegram/texts.py`) і конфігурації; внутрішній пакет у коді лишається нейтральним (`poweron`), щоб ребрендинг не зачіпав код. Тон текстів: теплий, простий, трохи з гумором, але без жартів, коли світла немає довго.

**Мета.** Бот у Telegram, який:
1. дає актуальний графік погодинних відключень (ГПВ) для адреси користувача (сьогодні/завтра);
2. сам пише, коли обленерго **оновило** графік;
3. нагадує перед вимкненням і перед поверненням світла.

**Аудиторія зараз:** власник і близькі (одиниці користувачів). Архітектура має допускати масштабування пізніше без переписування, але масштаб НЕ реалізуємо зараз.

**Не робимо зараз (non-goals):** HTTP API і мобільний застосунок (але архітектура під них закладається, див. розділи 3 і 13), RAG/LLM, вебінтерфейс, платежі, адмін-панель, webhook-режим, Postgres, багатомовність, групові чати, парсинг новин/каналів.

**Принципи:** мінімум залежностей, мінімум витрат на хостинг, чемне ставлення до чужого API (кеш, ліміти, ідентифікований User-Agent).

## 2. Джерело даних (неофіційне API, перевірено вручну)

База: `https://api-poweron.toe.com.ua/api`. Авторизації немає, потрібні лише GET із `Accept: application/json`. API неофіційне (це бекенд сайту `https://poweron.toe.com.ua`), формат може змінитися без попередження.

### 2.1 Ендпоінти

| Ціль | Запит | Примітки |
|---|---|---|
| Населені пункти | `GET /pw_cities?pagination=false` | ~1301 записів. `{id, name, codeOtg, otg:{name}}`. Тернопіль: `id=1032`. Може повертатись масивом або `hydra:member`, обробити обидва формати |
| Вулиці | `GET /pw_streets?pagination=false&city.id={cityId}` | Тернопіль ~299. `{id, name}`, напр. `вул. Садова` (`id=9985`) |
| Будинки + підчерга | `GET /pw-accounts/building-names?cityId={}&streetId={}` | Відповідь `{filters, buildingNames:[{id, buildingName, chergGpv, chergGav, chergAchr, chergGvsp, chergSgav, disconnectionTask}]}`. `chergGpv` це підчерга, напр. `"4.1"` |
| Розклад ГПВ | `GET /a_gpv_g` | Див. 2.2 |
| Планові роботи | `GET /pw_accident_planeds?page=1&otg.id=&city.id=&street.id=` | Поля `dateEvent`, `datePlanIn`, місто, вулиця. Фаза 5 |

| Опції | `GET /options?option_key={key}` | `pw_gpv_image_today`, `pw_gpv_image_tomorrow`, `pw_gpv_nek_comand`. Станом на 2026-10-17 порожні, не покладатись |

Інші ендпоінти, які бачили в бандлі сайту (поза MVP): `/archive_gpv_graphs`, `/schedule_arhiv`, `/pw_accounts_by_acc`, `/pw_accounts`, `/check-light?number=`.

### 2.2 `/a_gpv_g`: як викликає клієнт сайту

Параметри (відтворюємо логіку клієнта сайту):
- `group` = підчерга, напр. `4.1` (це `chergGpv`);
- `after` = (сьогодні − 1 день) у форматі `YYYY-MM-DDT12:00:00+00:00`;
- `before` = завтрашня дата (початок доби) у форматі `YYYY-MM-DDT00:00:00+00:00`;
- `time` = рядок `{cityId}/{streetId}/{buildingName}` **без символів `/`**, тобто конкатенація, напр. `103299851`;
- заголовок `X-debug-key` = `base64(utf8("{cityId}/{streetId}/{buildingName}"))`. Клієнт сайту шле його завжди. Чи він обов'язковий, невідомо: перевірити (Фаза 0), але в клієнті відтворювати завжди.

Відповідь (Hydra/JSON-LD): `hydra:member` це масив об'єктів `ActualGpvGraph`:
```
{ "id": 46,
  "dateCreate": "2026-10-17T14:16:05Z",   // коли графік створено/оновлено (UTC)
  "dateGraph":  "2026-10-17T00:00:00Z",   // на яку добу
  "dataJson": { "4.1": { "times": { "00:00":"0", "00:30":"0", ..., "23:30":"..." } } } }
```
Клієнт сайту очікує до 2 елементів: `[0]` сьогодні, `[1]` завтра (завтра пізніше за сьогодні за `dateGraph`). Ключі `times` це 48 півгодинних слотів. Значення слотів: рядки `"0"`, `"1"`, `"10"` (можливо інші).

Приклад зафіксованого факту (для тестів): для `group=4.1`, 2026-10-17, слоти `10:30="10"`, `11:00…13:30="1"`, `14:00="10"`, решта `"0"`, далі в кінці доби є ще `19:30="10"`.

### 2.3 Невідоме: ОБОВ'ЯЗКОВО з'ясувати у Фазі 0
1. **Семантика значень слотів** (`0`, `1`, `10`, можливо інші). Гіпотеза: `0` світло є, `1` світла немає, `10` перехідний слот (початок/кінець вимкнення, напів-слот). Підтвердити порівнянням із візуальним графіком на сайті для відомої адреси.
2. **Часовий пояс** слотів (гіпотеза: локальний Europe/Kyiv, а `dateCreate` у UTC; `dateGraph` це календарна дата).
3. Чи потрібен `X-debug-key`; чи залежить відповідь від `time`, чи лише від `group`; чи містить `dataJson` усі підчерги чи лише запитану.
4. Чи є ліміти частоти (429), поведінка за Cloudflare, чи потрібен конкретний User-Agent.
5. Поведінка, коли графіка на завтра ще немає (1 елемент у `hydra:member`) або на сьогодні немає відключень (усі `0`, чи порожній список).
6. Чи можуть значення `chergGpv` бути «Не входить»/порожніми для деяких будинків (поведінка бота: повідомити, що для адреси графік не діє).

Результат Фази 0: файл `docs/api-notes.md` з підтвердженими фактами та **записаними реальними відповідями** у `tests/fixtures/*.json`. Якщо семантику слотів неможливо надійно визначити автоматично, зупинитися і попросити власника порівняти один розклад із сайтом (не вгадувати).

## 3. Архітектура

**Принцип: продукт це ядро (core), а Telegram-бот лише перший клієнт.** Пізніше з'являться мобільний застосунок (через власний HTTP API) та, можливо, вебвіджет. Вони мають підключатися як нові адаптери, без переписування ядра й без міграції даних.

Зараз: один контейнер, один процес (`poweron all`), всередині aiogram 3 (long polling) + APScheduler + SQLite. Без Redis, Celery, Postgres, вебсервера й домену. Але точки входу роздільні з першого дня (див. 3.2).

```
src/poweron/
  core/                       # не знає ні про Telegram, ні про HTTP, ні про toe API
    domain/                   # чиста логіка, без I/O
      models.py               # Address, Subqueue, Interval, DaySchedule, ScheduleVersion
      schedule.py             # slots -> intervals
      diff.py                 # порівняння версій графіка
      reminders.py            # розрахунок моментів нагадувань
      events.py               # ScheduleUpdated, ReminderDue, ... (структуровані події)
    services/                 # use cases; єдиний вхід для будь-якого клієнта
      catalog.py              # пошук міст / вулиць / будинків
      subscriptions.py        # add/list/remove/update settings, forget_user
      schedules.py            # get_schedule(sub_id, day), next_event(sub_id)
      polling.py              # опитати джерело, зберегти версію, згенерувати події
      notifications.py        # події -> outbox
    ports.py                  # Protocol-інтерфейси: ScheduleSource, CatalogSource, Repository, Notifier, Clock
  adapters/
    toe_api/                  # реалізує ScheduleSource/CatalogSource; єдине місце з URL, заголовками, сирим JSON
      client.py, models.py (pydantic), errors.py
    db/                       # SQLAlchemy 2.0 async; реалізує Repository
      tables.py, repository.py, migrations/ (Alembic)
    telegram/                 # бот: handlers/, keyboards.py, texts.py, fsm.py, notifier.py (TelegramNotifier)
    # пізніше: http_api/ (FastAPI для застосунку), push/ (FCM/APNs notifier)
  worker/                     # jobs: poll_schedules, tick_reminders, dispatch_outbox, refresh_catalog, resolve_groups
  config.py                   # pydantic-settings
  __main__.py                 # CLI: poweron bot | worker | all
```

Правила шарів (перевіряти в рев'ю; бажано `import-linter` у `make check`):
- `core` не імпортує нічого з `adapters`, `worker`, aiogram, httpx, SQLAlchemy. Лише stdlib + pydantic.
- Адаптери-клієнти (`telegram`, пізніше `http_api`) викликають **лише `core.services`**, ніколи репозиторій чи toe API напряму.
- Сервіси приймають і повертають доменні моделі та внутрішній `user_id`, ніколи `chat_id` чи об'єкти aiogram.
- `toe_api` валідує всі відповіді pydantic; при невідповідності схеми кидає `ApiSchemaError`.
- Тексти для людей живуть в адаптері (`telegram/texts.py`); ядро віддає структуровані дані, а не відформатований текст.

### 3.2 Процеси і зв'язок між ними
- Три ролі: `bot` (приймає команди), `worker` (опитування, нагадування, розсилка), пізніше `api`. Зараз усі в одному процесі (`poweron all`), але **між собою спілкуються лише через БД** (outbox), не через виклики в пам'яті.
- Так пізніше кожну роль можна винести в окремий контейнер і масштабувати незалежно. `worker` має бути в одному екземплярі (або з блокуванням у БД), бо це він опитує API.

### 3.3 Сповіщення через outbox
- Ядро не надсилає повідомлення саме. Воно записує події в таблицю `outbox` (структурований payload + `dedupe_key`).
- `dispatch_outbox` бере невідправлені записи й надсилає їх через `Notifier` для кожного каналу доставки користувача (зараз лише `telegram`, пізніше `fcm`/`apns`).
- Кожен канал сам рендерить payload у свій формат. Так ідемпотентність, повтори й нові канали вирішуються в одному місці.

### 3.1 Ключова ідея: кеш по підчергах, а не по користувачах
- Підписка = адреса + кешована підчерга (`cherg_gpv`).
- Розклад кешується по ключу `cherg_gpv` (+ `date_graph`).
- Опитуємо API лише по **унікальних підчергах, де є підписники**. Для запиту `time`/`X-debug-key` береться адреса будь-якого (репрезентативного) підписника цієї підчерги (залежить від результату Фази 0 п.3: якщо відповідь залежить лише від `group`, використовувати фіксований репрезентативний `time`).
- Кількість запитів до API не залежить від кількості користувачів.

## 4. Модель даних

SQLAlchemy 2.0 (async) + Alembic. Зараз драйвер `sqlite+aiosqlite`, перехід на Postgres = зміна `DATABASE_URL` + прогін міграцій. Тому: жодного SQLite-специфічного SQL, час зберігати в UTC (`DateTime(timezone=True)`), JSON-поля через тип `JSON`.

**Ключове рішення:** користувач має внутрішній `user_id`, а Telegram це лише одна з його «ідентичностей». Тоді користувач застосунку й користувач бота можуть бути однією людиною зі спільними підписками.

```
users(id PK, created_at, timezone DEFAULT 'Europe/Kyiv', locale DEFAULT 'uk')

identities(                                   -- як людина входить
  id PK, user_id FK, provider,                -- 'telegram' | пізніше 'device' | 'apple' | 'google'
  external_id,                                -- для telegram: chat_id
  created_at, UNIQUE(provider, external_id))

delivery_targets(                             -- куди слати сповіщення
  id PK, user_id FK, channel,                 -- 'telegram' | пізніше 'fcm' | 'apns'
  address,                                    -- chat_id / push-токен
  is_active DEFAULT true, created_at, UNIQUE(channel, address))

subscriptions(
  id PK, user_id FK, label,                   -- "Дім", "Мама"
  city_id, city_name, street_id, street_name, building_id, building_name,
  cherg_gpv,                                  -- напр. "4.1"
  notify_on_update DEFAULT true,
  remind_before_off_min DEFAULT 30,           -- 0 = вимк.
  remind_before_on_min  DEFAULT 0,
  created_at, cherg_checked_at)

schedule_versions(
  id PK, cherg_gpv, date_graph (DATE), date_create, data_hash, slots (JSON), fetched_at,
  UNIQUE(cherg_gpv, date_graph, data_hash))

outbox(
  id PK, user_id FK, kind,                    -- 'schedule_updated' | 'reminder_off' | 'reminder_on' | 'admin_alert' ...
  payload (JSON),                             -- структуровані дані, НЕ готовий текст
  dedupe_key UNIQUE, created_at, sent_at NULL, attempts DEFAULT 0, last_error NULL)

catalog_cache(key PK, value (JSON), fetched_at)   -- міста/вулиці/будинки, TTL 24 год
```

Приватність: зберігати лише ідентичність, канал доставки, адреси підписок і підчергу. `/forget` (і пізніше аналог у застосунку) видаляє користувача каскадно. У логах INFO не писати адреси й chat_id.

## 5. Доменна логіка

### 5.1 Слоти → інтервали
- Функція `parse_slots(times: dict[str,str], semantics) -> list[Interval]`, де `Interval(start, end, state)` у `Europe/Kyiv`.
- Семантика значень слотів **конфігурована таблицею** (`SlotState` enum + мапінг), заповнюється за результатами Фази 0. Невідоме значення не ігнорувати мовчки: логувати WARNING і позначати слот `UNKNOWN`; для користувача показувати інтервал із приміткою «уточнюйте на сайті».
- Злиття сусідніх слотів з однаковим станом в один інтервал.
- Коректна обробка кінця доби (інтервал через північ склеювати між двома `date_graph`, якщо є обидва).

### 5.2 Виявлення оновлення
Нова версія графіка = для пари `(cherg_gpv, date_graph)` змінився `data_hash` (хеш нормалізованого `times`), а не лише `dateCreate`. Також повідомляти, коли з'явився графік на завтра, якого раніше не було. Перше завантаження після додавання підписки **не** є «оновленням» (без пуша).

### 5.3 Diff для повідомлення
Показати, що змінилось: нові/зниклі інтервали вимкнень і «було → стало» для сьогодні/завтра. Якщо diff порожній за інтервалами, а змінився лише `dateCreate`, не слати пуш.

### 5.4 Нагадування
Задача `tick_reminders` щохвилини порівнює «зараз» (Europe/Kyiv) з найближчими межами інтервалів у кешованому розкладі й шле нагадування «за N хв до вимкнення / повернення світла». Нагадування записуються в `outbox` з `dedupe_key = remind:{sub_id}:{date}:{boundary_ts}:{kind}` (унікальність ключа гарантує, що дубля не буде). При оновленні графіка нагадування перераховуються від нового розкладу (запис в outbox створюється лише в момент, коли нагадування вже має піти, і завжди від актуальної версії графіка, тому застарілих нагадувань не буває).

## 6. Опитування API (scheduler)

| Job | Інтервал | Дія |
|---|---|---|
| `poll_schedules` | `POLL_INTERVAL_SEC` (за замовч. 300) + jitter ±20 с | для кожної унікальної підчерги з підписниками: запит `/a_gpv_g`, порівняння хешу, запис версії, події `schedule_updated` в outbox |
| `tick_reminders` | 60 с | нагадування (5.4) в outbox |
| `dispatch_outbox` | 5 с | надіслати невідправлене через `Notifier` кожного каналу; повтори з backoff, `attempts`/`last_error`; ліміт Telegram ≈25 повідомлень/с |
| `refresh_catalog` | за потреби/TTL 24 год | міста/вулиці/будинки з кешу `catalog_cache` |
| `resolve_groups` | раз на добу | перевірити, чи не змінилась `chergGpv` для кожної підписки; якщо змінилась, оновити й повідомити користувача |

Чемний клієнт:
- глобальний ліміт ≤ 1 запит/с, послідовні запити, без паралельного «обстрілу»;
- `User-Agent: poweron-bot/<version> (personal use; contact: <ENV CONTACT>)`;
- таймаут 30 с, retry з exponential backoff + jitter (макс. 3 спроби), повага до `Retry-After` при 429/503;
- circuit breaker: після N поспіль помилок призупинити опитування на зростаючий інтервал.

## 7. Користувацький досвід бота

Команди: `/start`, `/add`, `/list`, `/schedule`, `/next`, `/settings`, `/remove`, `/forget`, `/help`.

**`/add` (wizard на aiogram FSM):**
1. Користувач вводить частину назви міста → бот шукає по локальному кешу `pw_cities` (регістронезалежно, нормалізація `ё/є`, апострофів), показує до 8 кнопок (пагінація) → вибір.
2. Те саме для вулиці (`pw_streets` для обраного міста).
3. Номер будинку: показати кнопки з `building-names` (пагінація) і/або прийняти текст і зіставити.
4. Підтвердження: показати «Місто, вулиця, будинок, підчерга {X}», запропонувати назву (`label`).
5. Якщо `chergGpv` порожнє/«Не входить»: чесно повідомити, що для адреси ГПВ не діє, підписку не створювати.

**`/schedule`:** кнопки Сьогодні/Завтра. Вивід: заголовок із підчергою й часом оновлення (`dateCreate` у Europe/Kyiv), список інтервалів «🔴 10:30–14:00 немає світла», «🟢 14:00–19:30 є світло», загальна тривалість відключень за добу. Якщо графіка на завтра ще немає, написати це.

**`/next`:** найближча подія: «Світло вимкнуть о HH:MM (через X год Y хв)» або «Увімкнуть о HH:MM».

**Пуш про оновлення:** коротке повідомлення «Графік для {label} оновлено», diff, посилання на офіційний сайт.

**`/settings`:** за кожною підпискою: сповіщення про оновлення on/off, нагадування перед вимкненням (0/15/30/60 хв), перед поверненням.

Усі тексти в `texts.py`. У кожному повідомленні з графіком коротка примітка: «Графік може змінюватись упродовж дня. Орієнтуйтесь також на poweron.toe.com.ua».

## 9. Надійність і спостережуваність
- Валідація відповідей pydantic. При `ApiSchemaError` або серії помилок: алерт адміну в Telegram (rate-limited: не частіше разу на годину для одного типу), бот продовжує працювати на кешованих даних, а в `/schedule` показує, що дані можуть бути застарілими, з часом останнього успішного оновлення.
- Структуровані логи (JSON або key=value), без адрес на рівні INFO.
- Ідемпотентність розсилок через `outbox.dedupe_key` + `sent_at` (рестарт не дублює пуші).
- Якщо Telegram повертає «бот заблоковано користувачем», позначати `delivery_targets.is_active = false`.
- Graceful shutdown: дозавершити поточну розсилку.
- Команда `/status` лише для `ADMIN_CHAT_ID`: час останнього успішного опитування по підчергах, кількість підписок, версія.

## 10. Деплой
- `Dockerfile` (`python:3.14-slim`, залежності через `uv`), non-root користувач. У `pyproject.toml`: `requires-python = ">=3.13"`, цільова версія в Docker і CI 3.14.
- Перед фіксацією версії (Фаза 1): перевірити, що `uv sync` і весь набір тестів проходять на 3.14 (aiogram, pydantic v2, httpx, aiosqlite, APScheduler, pydantic-settings). Якщо якась залежність не має сумісного релізу, зафіксувати `python:3.13-slim` і записати причину в README.
- `docker-compose.yml`: один сервіс, volume `/data` для SQLite, `restart: unless-stopped`, ліміти ресурсів (≈256 МБ).
- Вимога до хостингу: будь-який дешевий VPS або сервер, що працює постійно. Порти назовні не відкривати (long polling).
- README: як створити бота в BotFather, як запустити, як зробити бекап SQLite (копія файлу).

## 12. Фази й критерії готовності

**Фаза 0. Верифікація API (без бота).** Скрипт `scripts/probe.py`, який для відомої адреси (напр. Тернопіль, вул. Садова, 1: `cityId=1032`, `streetId=9985`) викликає всі потрібні ендпоінти, зберігає фікстури й друкує інтервали за гіпотезою. Закрити всі пункти розділу 2.3, записати в `docs/api-notes.md`.
*Готово, коли:* семантика слотів і часовий пояс підтверджені (або явно запитано власника), фікстури збережені.

**Фаза 1. Ядро.** Структура пакета (розділ 3), `core/domain`, `core/ports.py`, `adapters/toe_api`, тести, `import-linter` з правилами шарів.
*Готово, коли:* тести зелені, інтервали з фікстури збігаються з очікуваними, `core` не імпортує адаптери.

**Фаза 2. Сховище + опитування + outbox.** SQLAlchemy + Alembic (SQLite), репозиторій, `core/services` (subscriptions, schedules, polling, notifications), `worker` з `poll_schedules` і `dispatch_outbox`, виявлення оновлень, diff. Notifier на цьому етапі можна підмінити фейком.
*Готово, коли:* інтеграційний тест «нова версія → один запис в outbox на підписника → dispatch → повторний цикл без дубля» проходить.

**Фаза 3. Бот.** `adapters/telegram`: `/start` (створює `user` + `identity` + `delivery_target`), `/add` wizard, `/list`, `/schedule`, `/next`, `/remove`, `/forget`, `TelegramNotifier`. Хендлери викликають лише сервіси.
*Готово, коли:* власник може додати свою адресу, побачити графік і отримати пуш після (змодельованого) оновлення.

**Фаза 4. Нагадування і налаштування.** `tick_reminders`, `/settings`, `resolve_groups`.

**Фаза 5. Планові роботи (опційно).** `/pw_accident_planeds` для вулиці підписки, пуш про нові планові роботи.

**Фаза 6. Деплой.** Dockerfile, compose, README, `/status`.
*Готово, коли:* бот працює в контейнері, переживає рестарт без дублів пушів.

Порядок дій для Claude Code: працювати фазами, після кожної фази комітити й коротко звітувати. Якщо щось у розділі 2.3 неможливо підтвердити автоматично, не вгадувати, а запитати власника.

## 13. Шлях до масштабу (НЕ реалізувати зараз, лише не зашкодити)

### 13.1 Мобільний застосунок (що додасться, коли до нього дійде)
- `adapters/http_api/` на FastAPI поверх тих самих `core.services`. OpenAPI-схема → згенерований клієнт для застосунку (Flutter / React Native / Swift).
- Орієнтовні ендпоінти: `GET /catalog/cities|streets|buildings`, `GET/POST/DELETE /subscriptions`, `GET /subscriptions/{id}/schedule?day=`, `GET /subscriptions/{id}/next`, `POST /devices` (push-токен), `DELETE /me`.
- Автентифікація: анонімна реєстрація пристрою (`identity.provider='device'`) → токен; пізніше вхід через Apple/Google. Зв'язування з Telegram: бот видає одноразовий код (`/link`), застосунок його вводить, і обидві ідентичності вказують на одного `user`.
- Сповіщення: `adapters/push/` з `FcmNotifier`/`ApnsNotifier`, новий `delivery_targets.channel`. Ядро й outbox не змінюються.
- Нагадування в застосунку краще робити **локальними сповіщеннями на пристрої** (застосунок знає розклад), а з сервера пушити лише «графік оновлено». Це дешевше й працює без інтернету.
- Віджет на головному екрані / Live Activity: «наступне вимкнення о 14:00» з тих самих даних `next_event`.

### 13.2 Інфраструктура
- SQLite → Postgres: зміна `DATABASE_URL` + `alembic upgrade head`.
- Long polling → webhook за reverse proxy (разом із появою `http_api`, бо домен і HTTPS тоді вже будуть).
- Ролі `bot` / `worker` / `api` в окремих контейнерах; `worker` один (або блокування в БД).
- Інші обленерго: ще одна реалізація `ScheduleSource` (наприклад, `adapters/dtek_api`) + поле `provider` у підписці й версіях графіка.

### 13.3 Продукт
- Група/канал для ОСББ.
- Узгодження з Тернопільобленерго перед публічним запуском.
- Опційно RAG по новинах обленерго для вільних питань («чому вчора вимикали довше?»).
